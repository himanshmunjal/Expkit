# Decision framework

Use this for every experiment analysed with ExpKit. Items 1-5 are fixed **before** launch
and written into the experiment's TOML config. Changing them after seeing data is
how false positives get in.

## Before launch

1. **Primary metric.** One metric that decides the test. It goes in `[primary]`.
2. **Guardrails.** Metrics that must not get worse (`[[guardrails]]`, with
   `higher_is_better` set). They are not corrected for multiplicity, on purpose: a
   missed harm costs more than a false alarm.
3. **MDE and sample size.** The smallest effect worth shipping. Get it from
   `expkit power` (CLI) or the app's calculator. If you use CUPED, enter the
   variance reduction (R², from `data/prepare.py`) to get the smaller required n.
4. **Duration.** Run whole weeks (7, 14, 21 or 28 days) so weekday/weekend mix is
   balanced, and run at least as long as step 3 requires.
5. **Monitoring plan.** Either analyse once at the end (fixed horizon), or use
   alpha spending / mSPRT if you will look early. Never peek with a fixed-horizon
   p-value: in ExpKit's peeking experiment, daily looks inflate the false-positive
   rate several-fold.

## Choosing the method

These recommendations come from A/A and injected-lift simulations on the real Stack Overflow
extract (DECISION D-050 to D-054):

| Metric type | Use | Avoid | Why |
|---|---|---|---|
| Count / mean with a pre-period | **CUPED** | capping (winsorization) | CUPED cut variance by 63% (answers) and 74% (comments) and gave 92% power with no bias. Capping at p99 had −56% bias and 2% CI coverage of the true lift |
| Count / mean, no pre-period | **Welch** | percentile bootstrap at n < 10k | Welch is conservative at small n (safe). The bootstrap had 8.5–9% false positives at n = 100 |
| Ratio of sums (e.g. accepted / answers) | **jackknife_ratio** (default) | delta at small n; naive per-user ratio | Delta had 20% false positives at n = 100 and 10% at 1,000. Naive is biased (+18%) |
| Binary | **Welch** (or CUPED if a pre-period exists) | none | Calibrated at all sizes tested |

**Sample size.** `answers_posted` is hard to move detectably. Even the full population
(~80k/arm) with CUPED needs about a **14% lift** for 80% power. Pick primary metrics with the
power calculator before launch, not after.

**Monitoring.** If you will look early, use **O'Brien-Fleming**. It keeps about 93% of
fixed-horizon power and stops early on average. Use mSPRT only when the number of looks is
open-ended: it is valid under unlimited peeking, but at a fixed horizon it has about half the
power. Daily naive peeking gave 24–28% false positives.

**SRM sensitivity.** At 20k users, the p < 0.001 check caught a 5% loss of treatment users only
61% of the time, and a 2% loss 3% of the time. A passing SRM check does not prove that logging
is clean.

## At readout: checks that must pass first

- **SRM** (chi-square, threshold p < 0.001). A failure makes the result **INVALID**,
  however good the metrics look. Typical causes: redirects or crashes that hit one
  arm, bot filtering applied unevenly, logging gaps, assignment cached incorrectly.
- **Data freshness / completeness** for the analysis window.

## Decision matrix (implemented in `expkit/report/readout.py`)

| # | Condition (checked in order)                                   | Decision        |
|---|----------------------------------------------------------------|-----------------|
| 1 | SRM fails                                                      | **INVALID**: investigate and do not decide |
| 2 | Any guardrail significantly worse                              | **DO NOT SHIP** |
| 3 | Primary significant in the good direction                      | **SHIP**        |
| 4 | Primary significant in the bad direction                       | **DO NOT SHIP** |
| 5 | CI entirely inside (−MDE, +MDE)                                | **DO NOT SHIP**: well-powered null, stop investing |
| 6 | Otherwise (CI covers both 0 and MDE-sized effects)             | **EXTEND** or redesign |
